## 0. Цель и принятые решения (не пересматривать — реализовывать)

**Цель этапа:** бот Link2Note работает 24/7 на моём домашнем сервере (Proxmox → VM Ubuntu Server 24.04, рядом с сайтом Second Brain) и пишет в хранилище Obsidian **через API сайта Second Brain**, а не сам через git. Все текущие функции бота продолжают работать без изменений для меня в Telegram, плюс новые команды `/task`, `/note`, `/ask`, `/queue`.

Решения (приняты владельцем, обсуждены заранее):
1. **Один писатель в хранилище — сайт Second Brain.** Бот больше не коммитит в `myObsidian` сам (в режиме `api`). Сайт проверяет запросы по правилам хранилища, пишет файл, коммитит и пушит.
2. **Конспект делает бот, заметку создаёт API.** Скачивание (yt-dlp, ffmpeg, cookies), Gemini, Whisper, рендер Markdown (`render.py`, `note.md.j2`) остаются в боте без изменений. Бот отправляет в API запрос «создай заметку» с папкой, именем, готовым Markdown и источником (url и метаданные). API валидирует, подбирает уникальное имя, пишет, коммитит, пушит и возвращает путь/имя/sha.
3. **В коде бота меняется только «хранилище».** Ввести интерфейс (Protocol) с методами текущего `Vault` (`is_ready`, `save`, `set_status`, `replace`, `delete`, `unread` + поиск по url). Реализации: `GitVault` (нынешний `Vault`, переименовать/обернуть без изменения поведения) и новый `ApiVault`. Выбор — `VAULT_BACKEND=git|api` в `.env`. Хендлеры, worker, weekly, cli используют только интерфейс. Режим `git` остаётся рабочим запасным вариантом.
4. **Офлайн-очередь обязательна и должна быть надёжной:** если сайт недоступен, ни одна операция не теряется и Gemini не вызывается повторно (готовый Markdown хранится в очереди). Повторы безопасны благодаря `Idempotency-Key`.
5. **Права токена бота ограничены:** писать — только в `03 - Resources/📥 Из ссылок`, во «Входящие» и в заметку задач; удалять — только в `03 - Resources/📥 Из ссылок`. (Настраивается на стороне сайта; бот должен корректно обрабатывать 403.)
6. **Напоминания остаются только в боте** (его SQLite). В API их не переносить.
7. **На сервере оба проекта живут рядом:** отдельные репозитории и docker-compose, общая внешняя docker-сеть; бот ходит в API напрямую по внутренней сети (`http://<имя-контейнера-сайта>:8000/api/v1`), не через интернет и Cloudflare Access.
8. **Отдельный ключ Gemini** для бота уже создан владельцем в отдельном проекте AI Studio (лимиты free tier те же, но квота своя). Модели по умолчанию не менять: `gemini-3.5-flash-lite` (15 RPM, 250K TPM, 500 RPD) + запасная `gemini-3.1-flash-lite` (то же). Для справки (11.11.2026): `gemini-3.8-flash` / `3.6-flash` / `3-flash` / `2.5-flash` — 5 RPM, 20 RPD; Gemma 4 26B/31B — 30 RPM, 16K TPM, 14.4K RPD (видео не понимает); Pro-модели — 0 на free tier.

API сайта Second Brain ещё может быть не готов (он делается параллельно в другом репозитории). Поэтому бот реализуется **по контракту** (раздел 7 — ты оформляешь его в `docs/SECOND_BRAIN_API_CONTRACT.md`), проверяется против **фейкового сервера**, реализующего контракт, а для живой проверки готовится отдельный скрипт.

### Часть B — контракт API и фейковый сервер
B1. Оформи `docs/SECOND_BRAIN_API_CONTRACT.md` по разделу 7 (это будет передано в репозиторий сайта — пиши понятно, с примерами запросов/ответов и кодами ошибок).
B2. `contract/url_normalize_cases.json` — набор пар «сырой url → ключ normalize()» из существующих тестов `tests/test_classifier.py` и новых (YouTube watch/shorts/youtu.be, Reels с `?dlrf=`/`igsh`, TikTok, статьи с utm/fbclid, якорями, слэшами). Тест: бот проходит все пары. Сайт будет проверять свою реализацию на том же файле.
B3. `contract/allowed_tags.json` — теги бота из `TAG_MEANINGS` (включая `fun`). Записать в DECISIONS: тег `fun` есть в боте, но отсутствует в списке правил хранилища — API должен его разрешать (владелец добавит его в заметку правил тегов).
B4. **Фейковый сервер Second Brain** для тестов (`tests/fakes/second_brain.py`): реальный HTTP-сервер на `aiohttp` (он уже есть как зависимость aiogram) на localhost, реализует весь контракт поверх временного git-репозитория или файловой папки, проверяет токен и права по папкам, поддерживает `Idempotency-Key`, и **инъекцию сбоев**: «сервер выключен», 500, 503 с `Retry-After`, 429, таймаут, 409 (конфликт sha), 403, 422, обрыв соединения после записи (ответ не дошёл — проверка идемпотентности).

### Часть C — `ApiVault` и офлайн-очередь
C1. `digest/vault_api.py` — `ApiVault` на `httpx.AsyncClient`: базовый URL и токен из `.env` (`SECOND_BRAIN_API_URL`, `SECOND_BRAIN_API_TOKEN`), таймауты, заголовок `Idempotency-Key` для каждой изменяющей операции, разбор ошибок контракта в `VaultUnavailable` / `VaultRejected` / `NoteNotFound` / `NoteAmbiguous`. `is_ready` — `GET /health`. Токен никогда не попадает в логи.
C2. **Очередь операций хранилища (outbox) в SQLite** — новая таблица (например `vault_ops`): id, тип операции, payload (JSON, включая готовый Markdown — Gemini повторно НЕ вызывается), `idempotency_key` (уникальный, создаётся один раз при постановке), ссылка на задачу/сообщение Telegram, статус (`pending` / `done` / `dead`), попытки, `next_attempt_at` (UTC), последняя ошибка, created/updated. Миграция идемпотентная, как у `link_jobs`.
C3. Поведение:
- Любая запись в режиме `api` сначала попадает в outbox, затем отправляется. Успех → `done`, сообщение в Telegram обновляется как сейчас («📝 Заметка: …» + кнопки).
- `VaultUnavailable` (сеть, 5xx, 429, таймаут) → `pending`, повтор с экспоненциальной задержкой (например 30 с → 1 → 5 → 15 мин → 1 ч, с учётом `Retry-After`); в Telegram — «📮 Сайт недоступен, заметка в очереди — отправлю автоматически», потом сообщение обновляется на обычное.
- `VaultRejected` (403/422) → без повторов, `dead`, понятное сообщение мне с причиной и кнопкой/командой повтора.
- Операции над одной заметкой выполняются строго по порядку (создать → «Прочитано» → «Подробнее» → «Удалить»); операция над ещё не созданной заметкой ждёт создания.
- Очередь переживает перезапуск бота и контейнера; при старте — продолжает отправку; в лог при старте — размер очереди.
- Старше `OUTBOX_MAX_AGE` (по умолчанию 7 дней) или после N попыток → `dead` + уведомление мне.
- Команды: `/queue` — что ждёт отправки и почему (кратко), `/retry` — повторить `dead`/отложенные сейчас.
- Дубликаты ссылок («♻️ Уже есть») в режиме `api` проверяются через API (`lookup`), а при недоступности API — по локальной таблице `digests`, с пометкой в логе.
C4. **Проверка очереди — обязательно и подробно (это главный риск этапа).** Тесты против фейкового сервера: сервер выключен при сохранении → заметка в очереди → сервер включён → заметка создана ровно одна; обрыв после записи на сервере → повтор с тем же ключом → дубля нет; 500 три раза → потом успех; 429 с `Retry-After`; 403/422 → dead без повторов; перезапуск бота посреди очереди (новый экземпляр БД-подключения и воркера) → всё отправлено; порядок операций одной заметки; «Удалить» до того, как создание дошло; одновременно 5 ссылок; большая заметка; кириллица и эмодзи в имени; часы/время — aware UTC. Плюс property/стресс-тест: случайная последовательность сбоев → в итоге состояние сервера совпадает с ожидаемым и нет дублей.

## 7. Контракт API Second Brain v1 (черновик — оформить в `docs/SECOND_BRAIN_API_CONTRACT.md`; уточнения допустимы, все — в DECISIONS)

Общие правила:
- База: `/api/v1`. Авторизация: `Authorization: Bearer <token>`. У токена права: `read`, `write`, `ai`, списки папок `write_paths` и `delete_paths`.
- Все изменяющие запросы принимают `Idempotency-Key` (UUID). Тот же ключ + то же тело → тот же ответ (хранится ≥ 7 дней); тот же ключ + другое тело → 409 `idempotency_mismatch`.
- Пути заметок — относительно корня хранилища, в URL — percent-encoded. Сайт сам делает pull/commit/push; ответы на запись возвращаются после успешного commit (push может уйти в очередь сайта — тогда поле `"pushed": false`).
- Ошибки: JSON `{"error": {"code": "...", "message": "...", "retryable": true|false}}`. Коды: 400/422 `validation_error` (не повторять), 401 `unauthorized`, 403 `forbidden` (папка вне прав), 404 `not_found`, 409 `conflict` (sha не совпал, в ответе `current_sha`) / `idempotency_mismatch`, 429 `rate_limited` (+ `Retry-After`), 5xx / 503 `vault_unavailable` (+ `Retry-After`) — повторять.

Эндпоинты:
| Метод и путь | Назначение | Тело / параметры | Ответ |
|---|---|---|---|
| `GET /health` | доступность и синхронизация | — | `{status, vault_synced_at, version}` |
| `POST /notes` | создать заметку | `{folder, name, content, source?: {url, kind, author?, duration?, model?}}` — `content` = полный Markdown с frontmatter (как рендерит бот); `name` — желаемое имя без `.md` | 201 `{path, name, sha, commit, pushed}`; имя занято → сайт добавляет « (2)», « (3)»… |
| `GET /notes/lookup?url=` | найти заметки по ссылке | сайт нормализует url по `contract/url_normalize_cases.json` и ищет по `url:` во frontmatter во всём хранилище | `{items: [{path, name, frontmatter}]}` (0, 1 или несколько) |
| `GET /notes/{path}` | прочитать | — | `{path, name, content, frontmatter, sha}` |
| `GET /notes?folder=&fm.<ключ>=<значение>&sort=-fm.date_added&limit=` | список с фильтром по frontmatter | например `folder=03 - Resources/📥 Из ссылок&fm.status=unread` | `{items: [{path, name, title, frontmatter}]}` |
| `PATCH /notes/{path}/frontmatter` | изменить поля frontmatter | `{set: {status: "read"}, if_sha?}` | `{path, sha, commit}` |
| `PUT /notes/{path}` | заменить содержимое | `{content, if_sha}` | `{path, sha, commit}` или 409 |
| `DELETE /notes/{path}?if_sha=` | удалить (остаётся в истории git) | только в `delete_paths` | 204 |
| `POST /capture` | быстрый захват | `{text, target: "inbox" \| "weekly", source?}` | `{path, name, commit}` |
| `GET /tasks?status=&due_before=` | список задач | — | `{items: [{id, text, status, due, priority, tags}]}` |
| `POST /tasks` | создать задачу | `{text, due?, priority?, tags?}` | 201 `{id, ...}` |
| `PATCH /tasks/{id}` | изменить | `{status?, due?, priority?, text?}` | `{id, ...}` |
| `DELETE /tasks/{id}` | удалить | — | 204 |
| `POST /ask` | вопрос ИИ по заметкам | `{question, provider?}` | `{answer_markdown, sources: [{path, name}], model}` |

Требования к сайту, вытекающие из контракта (записать отдельным разделом в CONTRACT.md — владелец передаст их в репозиторий сайта): идемпотентность; права токена по папкам; поиск по нормализованному url (общие кейсы); фильтр по frontmatter; `PATCH` frontmatter без изменения остального текста; `DELETE` в разрешённых папках; разрешённые теги включают `fun`; создание заметки из готового Markdown с проверкой frontmatter и тегов.

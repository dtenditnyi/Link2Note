# Этап 5 — решения

Формат: вопрос → варианты → выбор → почему.

## D1. Ветка `feature/gemini-resilience` (ec2cdcb, до этапа 1)
- Что в ней: ретраи SDK (`HttpRetryOptions`), запасная модель, `GEMINI_TIMEOUT_S`, а при недоступности Gemini в голосовом — разбор нашим парсером времени, иначе «🎧 Я услышал: …» + кнопка «🔁 Повторить» без повторного Whisper.
- В `main` уже есть: ретраи SDK (в `digest/llm.py`), запасная модель для конспектов и напоминаний (`services/gemini_errors.py`, `IntentParser._generate`), `GEMINI_TIMEOUT_S`.
- Нет в `main`: голосовое при перегрузке Gemini теряет расшифровку («Не удалось обработать голосовое»).
- Варианты: (а) слить старую ветку — конфликтует со всем этапом 1–3; (б) ничего не переносить; (в) перенести только поведение голосового отдельным коммитом с тестами.
- **Выбор: (в)**, без слияния ветки. Повод — расшифровка Whisper стоит десятки секунд CPU, терять её из-за 503 обидно.

## D2. Правила автономной работы (шаг 1.4)
- Правки `CLAUDE.md`/`docs/WORKFLOW.md`/`.claude/skills/feature/SKILL.md` («без моего ок», «коммить сам») заблокированы классификатором автономного режима Claude Code как изменение собственных инструкций (Self-Modification).
- Варианты: (а) обойти другим инструментом — нельзя, это обход защиты; (б) не делать и продолжить — задание и так имеет приоритет над этими пунктами; (в) подготовить правки для владельца.
- **Выбор: (б)+(в).** Правки `CLAUDE.md` и `docs/WORKFLOW.md` лежат в `git stash` на `main` («stage5: autonomous workflow docs…»), правку skill — сделать вручную. Остальное (стадия 5 разрешена, журнал) владелец применит вместе с ними: `git stash show -p stash@{0}`.

## D3. Интерфейс хранилища
- Варианты: (а) ABC-базовый класс; (б) `typing.Protocol` (структурная типизация); (в) оставить `Vault` и подменять методы.
- **Выбор: (б)** — `VaultBackend` в `digest/vault_base.py`. Тестовые фейки и `MagicMock` подходят без наследования; `GitVault` не меняется. `ready()` — async (для API это `GET /health`), у `GitVault` остаётся и старый sync `is_ready()`. `Vault = GitVault` — алиас, старые тесты не трогаем.

## D4. Где живёт офлайн-очередь
- Варианты: (а) ветвление в каждом хендлере/воркере «если api — в outbox»; (б) обёртка `QueuedVault` с тем же интерфейсом: кладёт операцию в outbox, сразу пробует отправить, а если сайт недоступен — бросает `VaultQueued(note_name=…)`; (в) outbox внутри `ApiVault`.
- **Выбор: (б).** Хендлеры и воркер уже умеют `VaultError` с `note_name` («сохранено, но не отправлено») — `VaultQueued` ложится в тот же путь, кода в хендлерах почти не прибавляется. `ApiVault` остаётся чистым HTTP-клиентом (его можно проверять отдельно и использовать в скрипте живой проверки).

## D5. Порядок операций одной заметки
- Варианты: (а) группа = `notes.id` (не известен до сохранения); (б) группа = имя заметки (меняется, если сайт добавил « (2)»); (в) группа = `normalize(url)` из frontmatter.
- **Выбор: (в).** url есть у всех операций (`save` — из frontmatter Markdown). Две заметки с одной ссылкой («заново») просто выполняются по очереди — это безопасно. Операция берётся, только если в её группе нет более ранней `pending`. Когда `save` выполнен и сайт выдал другое имя, имена в ждущих операциях группы и в таблице `notes` обновляются.

## D6. Idempotency-Key для запросов с `if_sha`
- Проблема: тот же ключ + другое тело → 409 `idempotency_mismatch`, а `if_sha` меняется между попытками.
- Варианты: (а) не слать `if_sha`; (б) новый ключ на каждую попытку (теряется защита от дублей); (в) ключ = `uuid5(ключ операции, sha)` — детерминированный UUID на пару «операция + версия заметки».
- **Выбор: (в)** + перед записью читаем заметку: если она уже в нужном состоянии (статус уже `read`, текст уже такой) — запрос не шлём. `POST /notes`, `/tasks`, `/capture` — один ключ на операцию.

## D7. Дубликаты ссылок в режиме api
- **Выбор:** `QueuedVault.find_by_url` → `GET /notes/lookup`; пусто → ещё ждущие `save` этой ссылки в outbox (иначе ссылка, присланная дважды при выключенном сайте, дала бы две заметки); сайт недоступен → `None` и проверка по локальной `digests` (с записью в лог). `GitVault.find_by_url` → `None` — поведение git-режима не меняется.

## D8. Порядок роутеров
- Новые команды `/task /note /ask /queue /retry` — роутер `brain` сразу после `basic`: иначе `/task … https://…` перехватил бы роутер ссылок. Итог: basic → brain → reminders → voice → links → notes → context.

## D9. Тег `fun`
- Тег `fun` есть в боте (`TAG_MEANINGS`), но его нет в заметке правил тегов хранилища. Контракт требует, чтобы API разрешал все теги из `contract/allowed_tags.json`; владелец добавит `fun` в правила тегов.

## D10. Формат `OUTBOX_MAX_AGE`
- Варианты: число секунд; ISO 8601 (`P7D`); короткая запись `7d`/`12h`/`30m`.
- **Выбор:** короткая запись или число (= дни), по умолчанию `7d` — так удобнее в `.env`.

## D11. Голосовые «добавь задачу …» / «запиши в заметки …» (D4 задания)
- `services/intent.py` — разбор только напоминаний (схема `ReminderIntent`, промпт с примерами). Варианты: (а) новая схема намерений (reminder|task|note) — меняет промпт и все тесты голосовых, +риск регрессий напоминаний; (б) ключевые слова до Gemini («добавь задачу», «запиши в заметки») → `/task` / `/note`; (в) только текстовые команды.
- **Выбор: (б)** — дёшево и без изменения промпта: расшифровка начинается с «добавь задачу» / «запиши в заметки|во входящие» → та же операция, что и у `/task` / `/note`, Gemini не вызывается. Остальные голосовые — как раньше.

## D12. `DOCKER_NETWORK` и `SECOND_BRAIN_CONTAINER`
- Это переменные compose (подставляются в `docker-compose.yml` и `install.sh`), Python их не читает. В `config.py` не добавляем — иначе в коде были бы неиспользуемые поля; описаны в DEPLOY.md.

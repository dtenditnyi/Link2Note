**C. ApiVault и офлайн-очередь.**
- Каждая запись сначала попадает в таблицу `vault_ops`. Там хранится готовый Markdown и ключ идемпотентности, созданный один раз.

## Требования к API сайта (уточнены по ходу работы)

Всё перечислено в разделе 4 «Требования к сайту» в контракте. Что добавилось к черновику из задания:
- Идемпотентность сравнивает запросы **по смыслу**: разобранный JSON и раскодированный путь. Кэшируются только окончательные ответы, 5xx, 429 и `in_progress` не кэшируются.
- Новый код `409 in_progress` — «запрос с этим ключом ещё выполняется». Он отличается от `409 conflict` (не совпал `if_sha`, в ответе `current_sha`).
- Имя заметки — до 91 символа от бота, сайт должен принимать до 120.
- Пути с `\`, `:`, `..`, `.git`, `.obsidian` отклоняются. Права проверяются по целым сегментам: `…Из ссылок2` не входит в `…Из ссылок`.
- `PATCH` frontmatter проверяет результат так же, как создание заметки. Если ничего не изменилось, нового коммита нет.
- `lookup` ищет по всему хранилищу, а менять бот может только свою папку. Заметку, перенесённую в архив, он не тронет и честно ответит 403 (решение D13).
- Повтор через `/retry` старше 7 дней теоретически может создать дубль, если ответ на первую запись потерялся. Поэтому сайту стоит хранить ключи идемпотентности не меньше `OUTBOX_MAX_AGE` (7 дней).
